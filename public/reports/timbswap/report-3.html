TimbReleaseVault: the round oracle is immutable and points at a registry that has no cumulativeRounds and is replaced on every migration, so the 50M TIMBS it holds can never be released

Reporter: Ramprasad Edigi (Ram) Contract: TimbReleaseVault (mainnet source, contracts/TimbReleaseVault.sol, github.com/0xTimberZx/TimbSwap, main at commit 062634a) Suggested tier: T2 (value stuck, not stolen). The maintainers may rate it higher, since nothing can ever recover it. Relation to known issues: new. No TS-001..TS-052 entry touches TimbReleaseVault. Like TS-047 (TimbAirdropDistributor), this is a contract marked “design stub” in contracts/.

Summary

TimbReleaseVault is meant to hold the locked half of genesis supply (its header: “mint 50M to the treasury directly and 50M to this vault”) and release half of what is left at round 1,000, 2,000, 4,000 and so on. It has no owner and no rescue function. The only way out is release(), which reads rounds.cumulativeRounds().

rounds is set once in the constructor and is documented as “Provided by GameRegistry”. Two things break that:

  1. No GameRegistry has cumulativeRounds(). It does not exist anywhere in contracts/. Wired as documented, every release() call reverts on the missing selector, forever.
  2. The oracle cannot follow a migration. The project’s own migration path deploys a fresh GameRegistry per generation (scripts/DeployGen3Migration.s.sol, scripts/DeployBeta.s.sol; see TS-043). The vault keeps reading the retired registry, whose count stops moving. Even after a counter is added and seeded across generations, the vault never sees rounds played on the new registry.

The interface comment says the count “MUST never reset across game-generation redeploys”, but the contract binds it to a single registry address that the protocol replaces on each redeploy.

Root cause

IRoundOracle public immutable rounds;          // set once, no setter, no owner

function release() external {
    uint256 cum = rounds.cumulativeRounds();   // GameRegistry has no such function
    ...
    require(payout > 0, "nothing matured");
    timbs.safeTransfer(treasury, payout);      // the only exit for the TIMBS
}

The release schedule depends on one immutable external address. The protocol’s own migration process replaces that address, and the function the vault calls has not been written.

Impact

  • If deployed per its genesis split, 50,000,000 TIMBS (half of HARD_CAP) is locked with no exit. The failure only shows up at the first milestone (round 1,000), long after funding, and by then nothing can fix it.
  • If a cumulativeRounds() is later added to GameRegistry, the schedule still freezes at the first generation migration. That is the routine path the repo already uses, and the beta deploy itself deploys a new registry.
  • No user funds are involved and nothing is stolen. This is protocol supply stuck for good, which is why it is filed at T2.

Proof of concept

Foundry tests against an unmodified copy of contracts/TimbReleaseVault.sol and contracts/GameRegistry.sol from main 062634a. Local only, no network transactions.

test/ReleaseVaultOracle.t.sol:

function test_realRegistryAsOracle_releaseRevertsForever() public {
    GameRegistry reg = new GameRegistry(address(timbs), address(0x51CC), address(0), 1e18, 1e17);
    TimbReleaseVault v = new TimbReleaseVault(timbs, treasury, IRoundOracle(address(reg)), 50_000_000e18);
    timbs.transfer(address(v), 50_000_000e18);

    vm.warp(block.timestamp + 3650 days);
    vm.expectRevert();               // missing cumulativeRounds() selector
    v.release();
    assertEq(timbs.balanceOf(address(v)), 50_000_000e18);
}

function test_registryMigration_freezesReleaseSchedule() public {
    CountingRegistry oldReg = new CountingRegistry();       // a registry WITH a counter
    TimbReleaseVault v = new TimbReleaseVault(timbs, treasury, oldReg, 50_000_000e18);
    timbs.transfer(address(v), 50_000_000e18);
    oldReg.bump(600);                                       // generation N, then migration
    CountingRegistry newReg = new CountingRegistry();
    newReg.bump(600); newReg.bump(10_000);                  // seeded, keeps counting
    vm.expectRevert(bytes("nothing matured"));
    v.release();                                            // still reads the old 600
}

The file also has test_control_counterReachesMilestone_releasesHalf: the same vault wired to a counter that reaches 1,000 releases 25M, so the tests isolate the oracle wiring.

Suggested fix

Keep the vault ownerless, but read rounds from a small, permanent ledger instead of from a registry that gets replaced:

  1. Add an immutable RoundLedger contract that only ever counts up. The timelock owner can switch which registry is allowed to report, and the count carries across that switch.
  2. Each GameRegistry (or TimbPrize) calls ledger.recordRound() on every settled round.
  3. Deploy TimbReleaseVault with rounds = RoundLedger.
contract RoundLedger is Ownable2Step {        // owner = timelock
    uint256 public cumulativeRounds;          // never decreases, never resets
    address public reporter;                  // the live registry
    function setReporter(address r) external onlyOwner { reporter = r; }
    function recordRound() external {
        require(msg.sender == reporter, "not reporter");
        cumulativeRounds += 1;
    }
}

A migration then only calls setReporter(newRegistry). Also, until a real counter exists, do not fund the vault. A one-line pre-flight in the deploy script, IRoundOracle(rounds).cumulativeRounds() succeeding, would have caught the missing selector before any TIMBS was sent.

TimbGovernance: withdrawn voting power still votes at full weight, escapes the vote lock, and is removed from the quorum base

Reporter: Ramprasad Edigi (Ram) Contract: TimbGovernance (mainnet source, contracts/TimbGovernance.sol, github.com/0xTimberZx/TimbSwap, commit 3e97004) Listed deployment: Arbitrum One 0x26d1e27132d1d5cdb449d641938c7da26cd5be63 (see note on deployed build below) Suggested tier: T3, off-chain-signalling governance manipulation (voting-power / quorum bypass), per the repository SECURITY.md table Not a duplicate of: TS-021, TS-034, TS-040. This is the interaction between the TS-021 and TS-034 fixes.

Summary

Since TS-034, castVote weighs a vote by votingPowerAt(voter, p.createdAt), the creation snapshot. It never checks that the power is still deposited.

Since TS-021, every withdrawVotingPower ratchets each open proposal’s totalVotingPower (the quorum base) down to the live total.

So a holder who had power at creation can:

  1. withdraw everything right after the proposal is created (no lock exists yet, because they have not voted),
  2. get the tokens back and sell or move them,
  3. still vote later with the full snapshot weight.

The same power is removed from the quorum base and still counted in the votes. votingLockUntil is set on the vote, but it guards a balance that is already zero, so the “votes stay locked until the execution deadline” guarantee (audit M6) does not hold.

Root cause

// castVote
uint256 power = votingPowerAt(msg.sender, p.createdAt);   // snapshot only
if (power == 0) revert InsufficientVotingPower();
...
if (p.executionDeadline > votingLockUntil[msg.sender]) {
    votingLockUntil[msg.sender] = p.executionDeadline;    // locks a 0 balance
}

// withdrawVotingPower
uint256 lockedUntil = votingLockUntil[voter];             // 0 before voting
...
_sweepOpenProposals(true);  // TS-021: base ratchets down to live total

The snapshot answers “did you hold power at creation”, but not “do you still hold it”. The lock only works if the vote comes before the withdrawal, and nothing enforces that order.

Impact

  • Quorum bypass. Withdrawn power drops out of the denominator but still counts in the numerator. In the PoC, with the repo’s own test parameters (4% quorum), a proposal backed by 3.9% of creation power passes. It would fail if the backer kept the deposit.
  • Votes above 100% of the base. If whales exit and then vote, forVotes can be many times p.totalVotingPower (90e18 votes against a 1e18 base in the PoC).
  • Zero-stake voting. A wallet that has sold its whole position fully cancels a holder who stayed and is locked (50e18 vs 50e18 in the PoC).
  • Vote lock defeated. Voters keep no skin in the game through executionDeadline. “Vote and dump” works on every open proposal.

Governance is signalling-only during the beta: execution is owner-gated and real authority is the timelock and multisig. So no funds are directly at risk. That is why this is filed as T3, the tier the program names for voting-power and quorum bypass.

Proof of concept

A Foundry test runs against an unmodified copy of contracts/TimbGovernance.sol from commit 3e97004, using the same constructor parameters as tests/TimbGovernance.t.sol (threshold 1,000e18, quorum 400 bps, 3 day period, 1 day delay). Everything runs locally. No transactions were sent to any network.

test/GovWithdrawThenVote.t.sol:

function test_exploit_withdrawThenVote_passesBelowQuorum_unlocked() public {
    _deposit(honest, 95e18);
    _deposit(attacker, 3.9e18);
    _deposit(address(0xD00D), 1.1e18);
    uint256 pid = gov.createProposal("p", "d");    // base 100e18, quorum 4e18

    vm.prank(attacker);
    gov.withdrawVotingPower(3.9e18);               // base ratchets to 96.1e18
    vm.prank(attacker);
    timbs.transfer(buyer, 3.9e18);                 // tokens sold
    assertEq(gov.votingPowerDeposited(attacker), 0);

    vm.warp(block.timestamp + VOTING_DELAY + 1);
    vm.prank(attacker);
    gov.castVote(pid, true);                       // counts 3.9e18
    // quorum 4% of 96.1e18 = 3.844e18 <= 3.9e18

    vm.warp(block.timestamp + VOTING_PERIOD + 1);
    gov.executeProposal(pid);                      // Passed -> Executed
}

Recommended fix

Count only power that is both held at creation and still deposited, so that the vote lock actually covers what was counted:

uint256 power = votingPowerAt(msg.sender, p.createdAt);
uint256 held  = votingPowerDeposited[msg.sender];
if (held < power) power = held;
if (power == 0) revert InsufficientVotingPower();

This keeps TS-034, because a deposit made after creation still has a snapshot of 0. It keeps TS-021, because the ratchet is unchanged. It also closes the gap: once the voter votes, the counted amount is locked until executionDeadline.

test/GovFix.t.sol applies exactly this change. All three tests pass:

  • withdrawn power reverts with InsufficientVotingPower
  • a late deposit still cannot vote
  • an honest holder votes and is locked

An alternative is to lock power at proposal creation for anyone who held it. That is heavier and blocks honest exits, so the min above is the smaller change.

Note on the deployed build

A read-only eth_getCode on 0x26d1e27132d1d5cdb449d641938c7da26cd5be63 (Arbitrum One) shows bytecode without the openProposalCount() / votingPowerAt(address,uint256) selectors. So the live contract predates the TS-021 and TS-034 fixes. It currently reports proposalCount() = 0 and totalVotingPower() = 0.

This issue is in the current mainnet source that carries those fixes, which is the build the program says will replace it. It was reported the same way as TS-021, TS-034 and TS-040, which are tagged “(mainnet)” and were fixed in source. If the program only pays for the deployed bytecode, please treat this as a fix review of TS-021 and TS-034.

TimbGovernance: the TS-050 fix is bypassed by a withdraw and redeposit round trip, so withdrawn power still leaves the quorum base and still votes

Reporter: Ramprasad Edigi (Ram) Contract: TimbGovernance (mainnet source, contracts/TimbGovernance.sol, github.com/0xTimberZx/TimbSwap, main at commit 699a768, which includes the TS-050 fix from #177) Suggested tier: T3, off-chain-signalling governance manipulation (voting-power / quorum bypass), per the SECURITY.md table Relation to known issues: fix review of TS-050 (and of the TS-021 / TS-034 pair it sits between). The TS-050 fix closes the “withdraw and sell” path but not the “withdraw and put it back” path. The root cause that TS-050 described is still reachable.

Summary

TS-050 changed castVote to count min(votingPowerAt(voter, createdAt), votingPowerDeposited[voter]). That stops a voter who withdrew and kept the tokens out.

It does not stop a voter who withdraws and then deposits the same amount again:

  1. After a proposal is created, the holder calls withdrawVotingPower(x). TS-021 ratchets the proposal’s totalVotingPower (the quorum base) down by x.
  2. In the same block, the holder calls depositVotingPower(x). The live total goes back up, but the base never rises again, by design.
  3. At vote time, the snapshot is still x and held is x again, so the vote counts x.

The same x is out of the denominator and in the numerator. No tokens need to be sold or borrowed, the round trip costs two transactions of gas, and the vote lock then covers the redeposited balance, so the voter loses nothing.

Root cause

// withdrawVotingPower
votingPowerDeposited[voter] -= amount;
totalVotingPower -= amount;
_checkpoint(voter);
_sweepOpenProposals(true);              // base := min(base, live total)

// castVote (after TS-050)
uint256 power = votingPowerAt(msg.sender, p.createdAt);   // snapshot at creation
uint256 held  = votingPowerDeposited[msg.sender];         // balance NOW
if (held < power) power = held;

held is read at vote time only. The ratchet is driven by the lowest balance during the voting window. A balance that dipped and came back passes the held check, so the two sides still disagree about whether that power is “in” the proposal.

Impact

  • Quorum bypass. With the repo’s own test parameters (4% quorum), a proposal backed only by a holder of 3.9% of creation power passes after one round trip. Without the round trip the same vote fails quorum.
  • Votes far above the base. If nine of ten equal holders round-trip, the base falls to 10e18 while 90e18 is counted FOR, nine times the base, with every voter fully deposited.
  • No cost, no risk. Unlike TS-050, the attacker never gives up the tokens, so the M6 lock does not deter it.

Governance is signalling-only during the beta and execution is owner-gated, so no funds move. That is why this is filed at T3, the tier the program names for voting-power and quorum bypass.

Proof of concept

Foundry tests against an unmodified copy of contracts/TimbGovernance.sol from main 699a768, with the constructor parameters from tests/TimbGovernance.t.sol (threshold 1,000e18, quorum 400 bps, 3 day period, 1 day delay). Local only, no network transactions.

test/GovRoundTripBypass.t.sol:

function test_exploit_roundTrip_passesBelowQuorum() public {
    _deposit(honest, 95e18);
    _deposit(attacker, 3.9e18);
    _deposit(passive, 1.1e18);
    uint256 pid = gov.createProposal("p", "d");     // base 100e18, quorum 4e18

    vm.warp(block.timestamp + 1 hours);
    vm.startPrank(attacker);
    gov.withdrawVotingPower(3.9e18);                 // base ratchets to 96.1e18
    timbs.approve(address(gov), 3.9e18);
    gov.depositVotingPower(3.9e18);                  // held back to 3.9e18
    vm.stopPrank();

    vm.warp(block.timestamp + VOTING_DELAY + 1);
    vm.prank(attacker);
    gov.castVote(pid, true);                         // counts 3.9e18 >= 3.844e18

    vm.warp(block.timestamp + VOTING_PERIOD + 1);
    gov.executeProposal(pid);                        // Passed -> Executed
}

Suggested fix

Record, per open proposal, how much each voter withdrew while it was open, and subtract it from the snapshot at vote time. The withdraw path already walks the open list (at most 16 entries), so this stays bounded:

mapping(uint256 => mapping(address => uint256)) public withdrawnDuring;

// withdrawVotingPower, after _sweepOpenProposals(true):
for (uint256 i = 0; i < _openProposals.length; i++) {
    withdrawnDuring[_openProposals[i]][voter] += amount;
}

// castVote:
uint256 power = votingPowerAt(msg.sender, p.createdAt);
uint256 gone  = withdrawnDuring[proposalId][msg.sender];
power = power > gone ? power - gone : 0;
uint256 held  = votingPowerDeposited[msg.sender];
if (held < power) power = held;

Power that left a proposal’s base can then never count in that proposal’s votes, whatever happens to the balance afterwards. Reading the minimum over checkpoints is not enough on its own, because same-second checkpoints overwrite each other and a same-block round trip leaves no dip in the history.

test/GovRoundTripFix.t.sol applies exactly this change (src/TimbGovernanceFixed.sol). All four tests pass:

  • a full round trip can no longer vote (InsufficientVotingPower)
  • a partial round trip (10 deposited, 6 out and back) counts 4
  • an honest holder still votes their full snapshot
  • a withdrawal made before the proposal existed is not penalised
